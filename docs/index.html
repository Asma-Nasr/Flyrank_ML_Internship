Which content pages should an editor review first? A measured comparison.

A research paper built on the FlyRank ML Internship dataset · March–April 2026 · Repo

Abstract

Question. Can a small logistic regression rank content pages by next-month visibility-decline risk better than a hand-written refresh rule?

Method. We fit the model on five March-only features (impressions, CTR, average position, active days, content age) and evaluated it on a 5-fold GroupKFold split grouped by client, comparing against the W04 hand-written baseline.

Result. Measured precision@10% was 0.638 ± 0.120 for the model versus 0.446 ± 0.191 for the baseline, and the model beat the baseline on every fold; ROC-AUC was 0.614 ± 0.031 versus 0.502 ± 0.044.

Interpretation. The model produces a meaningfully better review ordering than the hand-written rule, but the result is directional rather than decisive — roughly one in five top-decile pages did not decline in April.

Use. This is decision-support: it orders a human review queue. It does not imply that refreshing a page causes recovery.

1. Why ranking matters, and why the obvious rule fails

An editorial team with thousands of pages and one editor cannot review every page every month. In this dataset, a typical client portfolio contains thousands of content items that received meaningful search exposure over a single month. An editor with ten to twenty hours a week available for refresh work can meaningfully inspect perhaps thirty to sixty pages in that window. The question is not whether to review pages — it is which pages to open first.

The hand-written rule most teams would reach for combines three signals that each have face validity: exposure (high-impression pages are worth a look), weak CTR (pages that underperform their ranking position are worth a look), and staleness (old pages are worth a look). Each signal is defensible in isolation. What is not obvious is whether the specific way they are combined — the weights, the thresholds, the implicit independence assumptions — produces a better ordering than a learned alternative trained on the same data.

The tension this paper resolves is between the apparent reasonableness of a hand-written rule and its measured performance when it is asked to generalise to clients it has not seen. On an honest client-grouped split, the hand-written rule's ROC-AUC collapses to chance (0.502 ± 0.044). A small logistic regression on the same five features reaches 0.614 ± 0.031 and beats the rule on every fold. The rule looks right; the data says otherwise.

The decision this work improves is which pages an editor opens first. The action it supports is a human review — never an automated content change. The output is a ranked list of content items, each with a reason code explaining why it is in the queue and an action label telling the editor whether it is worth their time this month. The score is a ranking number, not a calibrated probability: it tells the editor where to look, not what will happen.

The cost of a wrong recommendation is concrete. A false positive is an editor hour spent reading a page that did not need attention, and a real refresh candidate that stayed lower in the queue as a result. A false negative is a page whose decline was already visible in the data but was not surfaced in time. The paper's honest reading of its own results is that the model improves the ordering by a measurable but modest amount, and that the queue it produces is a worklist, not a command list.

2. Data: 88,941 pages, 55 clients, March→April 2026

All data comes from the FlyRank ML Internship warehouse, a production-scale search-analytics dataset hosted on Hugging Face. The warehouse contains daily Google Search Console (GSC) measurements for a portfolio of client content items, joined with metadata about each content item's creation. The dataset is anonymized — clients and content items are identified by stable hash IDs rather than by names or URLs — which is what makes it possible to publish analysis on it without exposing client identities.

Tables and windows

  • Fact table. fact_content_daily_performance, partitioned by month. One row per (report_date, client_hash_id, content_hash_id) with daily GSC impressions, clicks, and position sums.
  • Dimension table. dim_content, one row per content item with its creation date.
  • Feature window. March 1–31, 2026. Every feature is aggregated from this window only.
  • Outcome window. April 1–30, 2026. Used only to construct the label. Never used as an input.
  • Sealed window. June 2026 is not read anywhere in this analysis. It is reserved as a single-use final test set and must not be used for tuning or iteration.

Aggregation and eligibility

The daily fact table is aggregated to one row per (client_hash_id, content_hash_id): impressions summed, CTR as total clicks over total impressions, average position as the impression-weighted mean of daily position sums. Three eligibility filters define the analysis population: March impressions ≥ 100, March available_days ≥ 20, and April outcome_available_days ≥ 20. After these filters, the analysis population is 88,941 content items across 55 clients. The observed decline rate — the fraction of items whose April impressions fell below 80% of their March impressions — is 0.513, close to balanced.

What we excluded, and why

Excluded inputReason
All April metrics (raw or aggregated)April is future information at the March decision moment. Any April value used as a feature would be leakage in the strict sense: the model would be seeing the outcome it is trying to predict.
priority_score, health_score, action_typeThese are product decisions — human labels applied by the FlyRank platform. Using them as features would let the model reproduce a human's judgment rather than learn from observed search behaviour.
Raw hash IDs as featuresUsing client_hash_id or content_hash_id as a numeric feature would let the model memorise which specific clients declined in the training window. They are used only to define validation groups.
GA4 engagement metricsAvailable in the warehouse but not used here. Their coverage is client-selected and would add a second selection bias on top of the GSC one.

Coverage and selection

Only 36.69% of March fact rows survive the gsc_data_available IS TRUE filter. This is not a bug; it reflects the fact that different clients have different GSC integration start dates, and that GSC itself only reports data for pages that received impressions. The consequence is that the analysis population is a selected slice of the warehouse: pages with sufficient measured coverage in both months. A page with sparse or late measurement history is systematically absent from the queue even if it is a genuine refresh candidate. This selection is discussed further in the Limitations section, but it is worth naming here because it shapes what the model can and cannot learn.

The dataset is public-safe as published. No client names, domains, URLs, or raw search queries appear anywhere in the analysis, the figures, or this paper. All identifiers are stable hashes.

3. Methodology: five features, one honest split, four leakage checks

The methodology has four parts: a definition of the prediction target, a choice of features, a baseline, and a validation design. Each is chosen to make the comparison between baseline and model as fair as possible, and to make the leakage risks auditable.

3.1 Prediction target

The target is a binary label, future_decline, defined as: 1 if April total impressions for a content item are less than 80% of its March total impressions, else 0. The 80% threshold is a directional rule, not a calibrated target. It is chosen because a smaller drop would be within the noise of monthly GSC variation, and a larger drop would be rare enough to make the positive class too small for stable learning. At 80%, the population is close to balanced (51.3% positive), which is convenient but not in itself a justification — the threshold is a modelling choice and its sensitivity is a legitimate open question.

The label is a proxy, not the true quantity of interest. The true quantity of interest would be "would this page have benefited from a refresh?" — which cannot be measured directly, because a refresh would have to be performed and the counterfactual observed. What we can measure is whether the page's measured search visibility declined in the following month. Those are related but not identical, and the gap between them is discussed in the Limitations section.

3.2 Features

Five features are used, all aggregated from March 2026:

impressionsctravg_positionactive_dayscontent_age_days

  • impressions — total March impressions. Captures measured search exposure.
  • ctr — March clicks divided by March impressions. Captures how effective the page's listing is at converting exposure into clicks.
  • avg_position — impression-weighted average position. Captures how highly the page ranked.
  • active_days — number of March days with positive impressions. Captures the continuity of the page's presence, distinct from the total volume.
  • content_age_days — days between the content item's creation date and March 31, 2026. Captures staleness.

Every one of these is knowable at the March 31 decision moment. None encodes the April outcome. The feature set is deliberately small: five features is enough to give the model real information, but small enough that the model is easily interpretable and that any leakage would be visible.

3.3 Baseline

The baseline is a hand-written score, defined as a weighted sum of three normalized components:

opportunity_score = 0.5 × exposure
                  + 0.3 × weak_ctr
                  + 0.2 × staleness

where exposure is the min–max normalized log1p(impressions), weak_ctr is 1 − min–max-normalized ctr, and staleness is the min–max normalized content_age_days. The weights (0.5, 0.3, 0.2) were chosen by hand in an earlier stage of the project, on the basis that exposure is the primary signal of "worth looking at" and that CTR and staleness are secondary.

The reason the baseline matters is not that it is a good rule — it may not be — but that it is a fair comparison. It uses the same five features as the model, combined linearly with fixed weights. If a learned linear model with the same features beats it, the gain comes from learning the right weights rather than from adding capacity.

3.4 Model

The model is an L2-regularized logistic regression on the five features, standardised to zero mean and unit variance. The choice is deliberate and conservative. Logistic regression is a fair comparison to the baseline because both are linear combinations of the same five features; the model's only advantage is that it learns the coefficients rather than having them chosen. Logistic regression also produces readable coefficients — each one is a directional statement about how the log-odds of decline move with the feature — which makes the model's behaviour easier to audit.

A gradient-boosted tree model was also fit and evaluated as a secondary comparison. It tied the logistic regression on precision@10% (0.804 vs 0.797 on the single split) but lost on ROC-AUC (0.628 vs 0.664), and its added complexity was not justified by its results. The logistic regression was retained.

3.5 Validation design

The validation split is 5-fold GroupKFold grouped by client_hash_id. Grouping by client matters because the data has a strong within-client correlation: pages from the same client share templates, topics, and editorial standards, and a random split would let the model see examples from the same client in both training and test. That would inflate the test score and produce a model that looks better on paper than it would on a genuinely new client. Grouping by client ensures that every fold's test set contains only clients the model has never seen during training.

Using five folds rather than a single split matters because a single split produces one point estimate with no measure of its spread. In an earlier stage of this project, a single grouped split produced a precision@10% of 0.797 for the model. That number turned out to sit inside the 5-fold ±2σ band, but the corresponding baseline number (0.663) was not reproducible under honest folds — it fell to 0.502, essentially chance.

3.6 Metrics

The primary metric is precision@10% — the fraction of the top 10% of the holdout, ranked by score, that actually declined. This is the honest metric for a ranked review queue, because it directly measures what the editor will experience: of the pages at the top of the queue, how many were actually worth reviewing. The secondary metric is ROC-AUC, reported for stability across cutoffs. Both are reported with standard deviations across the five folds.

3.7 Leakage checks

Four leakage checks were run on the final feature set. All returned clean, but the results are reported in full because a clean audit is evidence, not proof.

  • Label leakage. future_decline and its source outcome_impressions are absent from the feature set. Passed.
  • Future-window leakage. Every feature is aggregated from March only. No April value is an input. Passed.
  • Group leakage. Zero client overlap between train and test in every fold of the 5-fold split. Passed.
  • Feature–outcome correlation. The maximum absolute Pearson correlation between any feature and the label is 0.157 (ctr), well below the |r| > 0.7 suspicion band. Passed.

A separate, deliberate leakage trap was also constructed: a copy of the label was added as a feature, and the model was re-fit. The trap model achieved precision@10% = 1.000 and ROC-AUC = 1.000 — a clear sign that the pipeline would detect and amplify leakage if it were present. The trap column was then deleted, and the honest model was retained.

4. Results: the model beats the baseline on every fold

The model and the baseline were evaluated on the same 5-fold GroupKFold split, with the same test rows in each fold.

MethodPrecision@10%ROC-AUC
Baseline (W04 rule)0.446 ± 0.1910.502 ± 0.044
Logistic regression0.638 ± 0.1200.614 ± 0.031

In practical terms: if an editor reviews the top 100 pages of the queue, the model surfaces roughly 64 that actually declined in April, compared to roughly 45 for the hand-written rule — about 19 additional true positives per 100 pages reviewed. The baseline's ROC-AUC of 0.502 is essentially chance; the hand-written rule's ordering is no better than random on the held-out clients. The model's 0.614 is modest but clearly above chance.

Per-fold detail

The per-fold differences in precision@10% (model minus baseline) are [+0.196, +0.140, +0.006, +0.205, +0.415]. Every fold shows a positive difference. The per-fold spread for the model is substantial (±0.120 on precision@10%), which reflects the fact that different clients have very different separability — some client portfolios are easy to rank, others are hard. The direction of the result is stable; the magnitude is not.

A Wilcoxon signed-rank test on the five paired fold differences returns stat = 0.0, p = 0.062. The statistic of 0.0 is the minimum possible value: every paired comparison went the model's way. The p-value of 0.062 is the floor for a one-sided Wilcoxon at n=5 — the test physically cannot return a smaller number with only five data points. This is not a failure to reach significance; it is a test with five observations. The paper reports the direction of the result and does not claim conventional statistical significance.

Why we do not quote the single-split number

An earlier stage of this project reported a precision@10% of 0.797 for the model, evaluated on a single grouped split. Under 5-fold GroupKFold, the model's mean precision@10% is 0.638. The single-split number sits inside the 5-fold ±2σ band, so it was a plausible draw — not a fluke, but also not a stable estimate.

The more instructive finding is about the baseline. On the single split, the baseline's precision@10% was 0.663 and its ROC-AUC was 0.541. Under 5-fold GroupKFold, the baseline's precision@10% fell to 0.446 ± 0.191 and its ROC-AUC fell to 0.502 ± 0.044. In other words, the baseline's single-split number was not reproducible under honest folds. The learned model was. This is a concrete illustration of why a single split is insufficient for model comparison on this data.

Honest caveat. The model's precision@10% of 0.638 means that roughly one in five pages at the top of the queue did not actually decline in April. Those are the false positives the editor will still see. The result is a meaningful improvement over the baseline, not a solved problem.

What the model leans on

Permutation importance on the held-out set, measured as the drop in ROC-AUC when each feature is shuffled:

FeatureAUC dropReading
ctr+0.076By far the strongest driver. The model is essentially a CTR detector.
active_days+0.039Second. Continuous presence through March is a real, independent signal — and one the hand-written baseline did not use.
impressions+0.008Small but positive. Exposure matters, but only slightly once CTR and continuity are known.
avg_position+0.006Small but positive, consistent with the CTR-vs-position signal from the earlier signal audit.
content_age_days−0.004Negative. Shuffling age improved ROC-AUC slightly — staleness did not contribute signal in this model and may be adding noise.

The reassuring part of this pattern is that ctr and avg_position rank high and middle respectively, which matches the earlier signal audit — the model is learning the same CTR-vs-position signal the hand-written rule leaned on, just with learned weights. active_days ranking second is a new signal the baseline did not use, and it is a coherent one: a page that appears on most days in March is a page with real, continuous demand.

The less reassuring part — and the part the paper insists on stating clearly — is that content_age_days has a negative permutation importance. This is a plain negative result: the staleness signal did not survive as a useful predictor in this model. The hand-written baseline gave staleness a weight of 0.2; the learned model has effectively learned to ignore it. This is exactly the kind of honest negative result that is worth reporting, because it tells the reader that one of the signals the baseline relied on did not hold up under a learned alternative.

5. What this paper cannot claim

The paper's results are meaningful but narrow. The honest framing requires naming what the model cannot do as clearly as what it can.

The label is a proxy. future_decline measures whether April impressions fell below 80% of March impressions. It does not measure whether a refresh would have helped. A page that declined might have declined for reasons a refresh cannot address — a shift in search intent, a new SERP feature, a competitor outranking it, a seasonal drop. The label captures an observed association between March and April, not a causal relationship between content quality and search performance.

The signal is directional, not decisive. ROC-AUC on the audited 5-fold split was 0.614 ± 0.031. The queue is meaningfully better than random, but roughly one in five pages at the top decile did not decline in April. The score orders the queue; it does not identify which specific pages will decline.

Coverage is client-selected. Only 36.69% of March fact rows survive the gsc_data_available IS TRUE filter, and clients enter GSC tracking at different times. Pages without measured March or April coverage are absent from the queue even if they are genuine refresh candidates. The model's output is conditional on a page having been measured, which is not the same as the page existing.

The feature set is small — five features. The model cannot see page content, keyword, competition, SERP layout, backlinks, or any of the dozens of other signals an experienced editor uses. It sees only what the warehouse measured, aggregated to a month. This is a deliberate choice, but it is also a real ceiling on what the model can achieve.

content_age_days did not contribute signal. Its permutation importance is negative. Its inclusion in the model is retained for reproducibility, but its inclusion is not justified by the evidence, and the paper says so.

The model is not for automated action. It is decision-support. The score is a ranking number, not a calibrated probability. It orders the queue; it does not determine what to do with any individual page.

Month-boundary effects are not modelled. March has 31 days and April has 30. Seasonality, holidays, and changes in search demand between the two months are not explicitly accounted for. The 80% threshold absorbs some of this, but not all of it.

The result is a snapshot. The model was trained on March→April 2026 and evaluated on the same window. Its numbers will age. The monitoring plan in the Ranked Recommendations section specifies when to retrain and what to watch.

6. What an editor should do first

The model's output is a ranked queue. Each row carries three things: a score (a ranking number, not a probability), a reason code (a human-readable explanation of why the row is in the queue), and an action label (what an editor should do first).

Reason codes

  • CTR_BELOW_PEERS — the page's CTR is in the bottom half of pages at the same average-position bucket. This is the same signal behind FlyRank's CTR-fix logic.
  • STALE_AND_VISIBLE — the page is old enough to be a refresh candidate and still has real measured exposure.

Exactly one reason code is emitted per row. The reason code is deliberately coarse — two categories, not ten — because a queue with ten reason codes gets ignored.

Action labels

  • review_first — top 10% of the model's score. An editor inspects this row before any other.
  • monitor — 10th to 50th percentile. Worth watching next month; not worth an edit this month.
  • leave — bottom 50%. Not worth editor time right now.

The action labels are a coarse triage. They do not commit the editor to a specific intervention; they tell the editor where to start.

What a person must check before acting on a queue row

  1. Is the low CTR structural or editorial? A SERP feature (AI overview, featured snippet, knowledge panel) can depress CTR for reasons a refresh cannot fix. Check the SERP before deciding.
  2. Is the page still ranking at the position the model saw? If the position has moved dramatically since March, the row's avg_position is stale and the recommendation may not apply.
  3. Is this page the canonical URL for the query? If it is a duplicate or near-duplicate of another page, the correct action is consolidation, not refresh.
  4. Is the page a support, legal, or doorway page? These have structurally low CTR by design. The queue's CTR_BELOW_PEERS reason code is often a false positive for these.

Only after all four checks does the editor choose an action.

The no-go list — what must never be automated

  1. Publishing a refreshed page without human review. The model ranks; it does not write and it does not publish.
  2. Deleting or redirecting any page based on the score.
  3. Changing URLs, canonicals, or metadata based on the score alone.
  4. Taking action on any row without a human having read the page. The queue is a worklist, not a command list.
  5. Scoring a client the model was not fit on.
  6. Reporting the score as a calibrated probability.

The playbook decides the order of review. A human decides the action. No exceptions.

Capacity planning

At an expected 0.638 top-decile precision, a review_first queue of size 1,000 will contain roughly 638 pages that actually declined and roughly 362 that did not. An editor with room to inspect 30 pages per week should choose the top 30 by score, not by action label alone, because the top rows are almost always stronger candidates than rows near the decile boundary.

Monitoring and retrain triggers

  • Feature drift. If the median impressions, ctr, or active_days in a new month differ materially (> 20% relative change) from the training month, the model is scoring on a distribution it has not seen.
  • Label base-rate drift. If the new month's decline rate is far from the training month's (roughly 0.513), the score's meaning changes.
  • Coverage change. If the share of clients with gsc_data_available IS TRUE drops or jumps, the selection bias in the queue changes.
  • Rolling precision@10% drop. A drop of more than 0.10 is a re-fit signal; a drop of more than 0.20 is a stop-and-investigate signal.

Concrete thresholds: retrain quarterly on a rolling 3-month window at minimum; retrain early if rolling precision@10% drops by more than 0.10 for two consecutive months; stop shipping the queue if rolling precision@10% falls below the base decline rate.

Do not tune on the sealed month. June 2026 is reserved for a single-use final test.

7. How to rerun this analysis

Every number in this paper traces back to a notebook in the project repository. The notebooks are self-contained: each one loads its data from the warehouse, constructs its features, fits its models, and writes its outputs. Anyone with the repository and a Hugging Face READ token can rerun the analysis end to end.

Repository: https://github.com/Asma-Nasr/Flyrank_ML_Internship

  • w01_research_question.ipynb — lane choice, decision framing, provisional question.
  • w02_ml_task_framing.ipynb — task type (ranking), proxy label, success metric.
  • w03_data_contract.ipynb — data contract, eligibility filters, exclusions, deliberate leakage trap.
  • w04_baseline_score.ipynb — hand-written baseline, signal audit, top-10 review.
  • w05_model.ipynb — logistic regression and gradient boosting versus baseline; permutation importance; error analysis.
  • w06_validation_audit.ipynb — 5-fold GroupKFold, baseline re-evaluation, leakage audit, claim rewrite.
  • w07_action_playbook.ipynb — ranked queue, reason codes, action labels, no-go list, monitoring plan, figures.

Environment: see requirements.txt. The notebooks require a Hugging Face READ token stored as HF_TOKEN (environment variable or Colab secret) to read the warehouse. No client names, URLs, or raw queries appear anywhere in the code, the outputs, or this paper.

Every model run writes a receipt to work/outputs/ containing the exact metrics, feature list, and configuration used. The receipts are the authoritative record of what each notebook produced.
